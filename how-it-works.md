# Visual Localization БПЛА — как это работает

Документ для разбора ТЗ: что происходит внутри сервиса, зачем каждый блок и как это защищать.

---

## 1. Задача простыми словами

У БПЛА есть GPS/INS с ошибкой (до нескольких км). Камера снимает землю почти сверху (надир).

**Идея:** сравнить снимок с спутниковой/картографической подложкой и найти, *куда* на карте этот кадр лучше всего ложится. Отсюда — уточнённые lat/lon центра кадра.

Это не «узнать город по фото», а **геопривязка кадра к карте** в окрестности уже известной приблизительной позиции.

```
снимок + грубые координаты  →  совпадение с картой  →  точные координаты + confidence
```

---

## 2. Ключевые понятия (их спросят на защите)

### GSD (Ground Sample Distance)

Сколько метров на земле приходится на **один пиксель** снимка.

Примерно (для надира):

```
GSD ≈ (высота_м × размер_пикселя_сенсора_мм) / фокусное_мм
```

Или через FOV:

```
ширина_кадра_на_земле ≈ 2 × высота × tan(HFOV/2)
GSD ≈ ширина_кадра_на_земле / ширина_изображения_в_пикселях
```

**Зачем:** zoom тайлов карты нужно выбирать так, чтобы «зернистость» карты была близка к GSD снимка.  
Если карта слишком крупная — мало деталей. Слишком мелкая — шум, лишние данные, медленнее.

| Высота | Типичный GSD (порядок) | Zoom тайлов (ориентир) |
|--------|------------------------|-------------------------|
| 100 м  | десятки см             | высокий (18–20)         |
| 300 м  | ~1 м                   | средний–высокий         |
| 600–800 м | метры               | ниже                    |

Точные числа зависят от камеры; на защите важно показать *логику*: высота ↑ → GSD ↑ → zoom ↓.

### Геопривязка (georeferencing)

Перевод «пиксель снимка» ↔ «точка на земле (lat/lon)».

При надире и известных высоте/углах/камере:

1. Луч из центра камеры идёт вниз (с поправкой на pitch/roll).
2. Пересечение с землёй ≈ центр кадра на местности.
3. По yaw понимаем, как повёрнут снимок относительно севера.
4. По FOV/focal считаем, какой прямоугольник земли виден в кадре.

**Pitch ≠ 0** ломает простую модель «прямоугольник = ортофото»: появляется перспектива, здания «заваливаются», matching с ортофото хуже.

### Error budget

Откуда берётся итоговая ошибка:

| Источник | Порядок влияния |
|----------|-----------------|
| Начальная ошибка GPS/INS | задаёт размер поиска (до 5 км) |
| Ошибка высоты | меняет масштаб кадра |
| Ошибка yaw | поворот → хуже match |
| Pitch/roll | перспектива vs ортофото |
| Устаревание карты / сезон | ложные/слабые matches |
| Алгоритм matching | residual, outliers |

## 3. Pipeline из ТЗ — что делает каждый блок

```
HTTP API  →  Georeferencer  →  Map Fetcher  →  Localizer
/localize     (photo→map)      (tiles)         (matching)
```

### 3.1. HTTP API (`POST /localize`)

Принимает multipart:

- `image` — снимок
- `lat_deg`, `lon_deg` — грубое положение
- `altitude_m`, `yaw/pitch/roll`
- камера: `focal_mm` + `sensor_*` **или** `hfov_deg` + разрешение
- опционально `search_radius_m` (default 5000)

Отдаёт уточнённые координаты, дельты, `confidence`, время, diagnostics.

Ошибки:

- **400** — кривой запрос (нет файла, NaN, высота вне диапазона…)
- **422** — алгоритм отработал, но **не нашёл** надёжного совпадения
- **500** — упал сервис (тайлы недоступны, баг…)

`GET /health` — просто `{"status":"ok"}`.

### 3.2. Georeferencer

**Вход:** метаданные полёта + размер изображения.  
**Выход:** описание области поиска на карте.

Типично считает:

1. **Центр поиска** — начальные lat/lon (иногда с поправкой на pitch: центр кадра ≠ надир).
2. **Радиус** — `search_radius_m` или default 5 км.
3. **Ожидаемый масштаб/GSD** снимка.
4. **Ориентацию** кадра относительно севера (yaw).
5. Опционально: bounding box «что примерно видит камера» при этих углах.

Это ещё **не** поиск по картинке — только геометрия: «где на Земле искать и с каким zoom».

Минимальная модель для прототипа (надир):

```
центр_поиска = (lat, lon)
zoom = f(altitude, focal, sensor, image_size)   # чтобы GSD_map ≈ GSD_query
bbox = круг/квадрат радиусом search_radius вокруг центра
```

### 3.3. Map Fetcher

**Вход:** bbox / центр + радиус + zoom.  
**Выход:** растр карты (или набор тайлов, склеенных в одно изображение) + его геопривязка (какие lat/lon у углов).

Источники (любой открытый, описать лицензию в README):

- Esri World Imagery
- Mapbox Satellite (free tier)
- Google Static Maps (лицензия строже — осторожно)
- OSM raster (для зданий/дорог; для «фото с воздуха» хуже, чем imagery)

Практика для прототипа:

1. Посчитать нужный zoom.
2. Скачать тайлы, покрывающие область.
3. Склеить в один `map.png` / numpy-массив.
4. Сохранить affine: пиксель карты ↔ lat/lon (или Web Mercator → WGS84).
5. Желательно **кэш** тайлов на диск (плюс на защите).

При ошибке 5 км область огромная → либо грубый zoom + потом refine, либо сетка патчей (см. §5).

### 3.4. Localizer (matching)

**Вход:** query-снимок + map-растр (+ геопривязка карты).  
**Выход:** смещение / поза + confidence (или «не сошлось»).

Базовый классический путь (хорошо для тестового):

```
1. Предобработка (grayscale, optionally CLAHE, resize к близкому GSD)
2. Детекция ключевых точек + дескрипторы (ORB / SIFT / AKAZE)
3. Matching дескрипторов (BF / FLANN + ratio test Lowe)
4. RANSAC → гомография (или аффинное / только сдвиг+поворот+масштаб)
5. По гомографии: куда попал центр query на map
6. Пиксель map → lat/lon
7. confidence из inliers / residual / coverage matches
```

**Почему RANSAC:** среди matches много ложных; RANSAC ищет модель, которой согласуется максимум точек.

**Что значит «нашли»:**

- гомография переводит центр query-изображения в точку `(x, y)` на карте;
- эта точка через georeference карты становится `(lat, lon)`;
- `delta_*` = уточнённые − исходные.

Простая альтернатива для демо (если features плохо работают на «симулированных» данных):

- template matching / phase correlation на нормализованных патчах;
- работает, когда query — буквально вырезанный кусок карты с шумом/поворотом (как в ТЗ разрешено симулировать).

## 4. Confidence — как оценивать и когда 422

Нет единого стандарта; для прототипа достаточно честной эвристики, например:

```
confidence = clip(
  w1 * (n_inliers / n_matches) +
  w2 * (1 - residual_normalized) +
  w3 * spatial_coverage,   # matches не в одном углу
  0, 1
)
```

Отклонять (422), если:

- слишком мало inliers (например &lt; 12–30);
- residual после RANSAC большой;
- matches скучены в одном углу (подозрительно);
- гомография «вырожденная» (огромный scale, отражение);
- лучший кандидат слабо лучше второго (ambiguity) — особенно при большом радиусе поиска.

На защите формулировка: *confidence — не вероятность в байесовском смысле, а эвристика качества match; порог калибруем на examples*.

## 5. Большая начальная ошибка (до 5 км)

На полном разрешении искать в круге 5 км — дорого и шумно.

Типичная схема **coarse-to-fine**:

1. **Грубо:** низкий zoom / уменьшенные изображения / place recognition (NetVLAD и т.п.) → несколько кандидатов.
2. **Уточнение:** вокруг топ-K кандидатов — высокий zoom + feature matching.
3. Выбор лучшего по score; если все слабые → 422.

Для прототипа без нейросетей:

- разбить область на сетку окон;
- на каждом окне быстрый score (ORB inliers или correlation);
- refine лучшие 3–5.

## 6. Как собрать examples/ (симуляция из ТЗ)

ТЗ явно разрешает:

1. Взять участок imagery.
2. Обрезать / повернуть / добавить шум / чуть изменить яркость.
3. Подать как `query.jpg` с **смещёнными** lat/lon на N метров.
4. Сервис должен «найти» истинный сдвиг.

Структура кейса:

```
examples/case_01_100m/
  query.jpg
  meta.json          # то, что уйдёт в POST /localize
  expected.json      # опционально ground truth
  result.json        # ответ сервиса
  visualization.png  # query | map | стрелка смещения
```

Кейсы по ТЗ:

| # | Высота | Ошибка старта | Смысл |
|---|--------|---------------|--------|
| 1 | ~100 м | ~500 м | лёгкий, высокий zoom |
| 2 | ~300 м | ~2 км | средний поиск |
| 3 | ~600 м | ~5 км | стресс радиуса |
| 4 | ~800 м | сезон/освещение ≠ карте | failure mode |

```
uav-visual-localization/
├── app/
│   ├── main.py           # FastAPI: /localize, /health
│   ├── models.py         # Pydantic: запрос/ответ
│   ├── georeferencer.py  # GSD, zoom, bbox, yaw
│   ├── map_fetcher.py    # тайлы + кэш + geotransform
│   └── localizer.py      # matching → lat/lon + confidence
├── examples/
├── tests/
├── requirements.txt
├── Dockerfile
└── README.md
```

Интерфейсы (смысл, не обязательно точные имена):

```python
class Georeferencer:
    def plan(self, meta, image_size) -> SearchPlan:
        """GSD, zoom, center, bbox, rotation hint."""

class MapFetcher:
    def fetch(self, plan: SearchPlan) -> MapRaster:
        """tiles → image + pixel_to_latlon."""

class Localizer:
    def localize(self, query, map_raster, plan) -> LocalizationResult:
        """match → lat/lon, deltas, confidence; или ошибка 'не сошлось'."""
```

Тяжёлые куски можно оставить как интерфейс + docstring «как реализовать по-взрослому» — ТЗ это допускает. Но **хотя бы 2 из 4** examples должны давать разумный результат.

## 8. Ограничения метода (заготовки для README §b) — минимум 5

1. **Сезон и освещение** — листва, снег, тени; дескрипторы не совпадают с картой другого времени.
2. **Однородная местность** — вода, поле, пустыня: мало уникальных точек → matching нестабилен.
3. **Устаревшая карта** — новые здания/дороги → ложные соответствия или провал.
4. **Сильный pitch/roll** — перспектива ≠ ортофото; простая гомография на «плоскую землю» врёт у горизонта.
5. **Погода / атмосфера** — облака, дымка, блики.
6. **Повтор местности** — одинаковые кварталы/лесополосы → ambiguity, ложный пик confidence.
7. **Thermal / ночь** — другой модальный домен; RGB-карта почти бесполезна без cross-modal моделей.
8. **Ошибка высоты/углов** — неверный масштаб/поворот ухудшает overlap и RANSAC.

## 9. Доработки (заготовки для README §c) — минимум 5 + куда смотреть

1. **Learned local features** — SuperPoint + SuperGlue / LightGlue — устойчивее ORB на смене освещения.  
   OSS: [SuperGlue](https://github.com/magicleap/SuperGluePretrainedNetwork), [LightGlue](https://github.com/cvg/LightGlue)

2. **Cross-view / UAV-to-satellite сети** — специально учат drone↔satellite.  
   Литература: University-1652, DenseUAV; работы по cross-view geo-localization.

3. **Hierarchical / coarse-to-fine + place recognition** — NetVLAD / AnyLoc для грубого поиска в 5 км, потом local refine.

4. **Учёт DEM / рельефа** — не плоская земля; лучше проекция лучей, меньше ошибка на холмах.

5. **Временные/сезонные карты** — несколько подложек, выбор по дате/сезону; или domain adaptation.

6. **IMU/INS fusion** — visual result как observation в фильтре (EKF/UKF) вместе с 10 Hz INS; камера 1 Hz.

7. **Thermal pipeline** — edge/structure matching, или обучаемый RGB↔LWIR; отдельный map layer.

8. **Онлайн-кэш и тайловый CDN** — latency для борта/сервера.

## 10. Ответы на вопросы защиты (шпаргалка)

**Как выбираете zoom при высоте и GSD?**  
Считаем GSD query → выбираем zoom, где GSD тайла ближайший (чуть мельче query — нормально). Формула Web Mercator: метров на пиксель зависит от широты и zoom.

**Ошибка 5 км — что делать?**  
Не матчить весь растр в полном разрешении. Coarse-to-fine / сетка окон / place recognition → refine. Иначе OOM и ложные matches.

**Как confidence и когда reject?**  
Inliers, residual, coverage, margin до 2-го кандидата. Ниже порога → 422.

**Ночной thermal (Boson LWIR)?**  
Другой домен: другой fetcher/карта или cross-modal matching; классический SIFT по RGB-satellite почти мёртв. Меняется Localizer (+ возможно предобработка edges).

**Pitch 15°?**  
Центр кадра смещён от надира; геометрия не орто. Нужна проекция луча + либо warp query «в надир», либо 3D/гомография с осторожностью; matching с ортофото деградирует.

**Бортовой контур 10 Hz INS + 1 Hz camera?**  
Visual localization — редкий absolute update; между кадрами — INS. Результат `/localize` кормит фильтр; нельзя блокировать управление на секунды без асинхронной очереди.

## 12. Одна формула потока данных

```
meta + image
    → Georeferencer: (center, radius, zoom, yaw)
    → MapFetcher: map_image + geotransform
    → Localizer: pixel_shift / H
    → geotransform(center_on_map) → lat, lon
    → deltas, confidence, diagnostics
```

Если на защите спросят «где магия» — она в **Localizer** (соответствие картинок).  
Если спросят «где инженерия» — в **GSD/zoom, радиусе поиска, confidence и отказе 422**.
